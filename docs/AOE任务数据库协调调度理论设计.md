# AOE任务数据库协调调度理论设计

## 一、目标与边界

本设计用于规范 AOE 在多智能体、多任务并发场景下对任务数据库与业务数据库的读写协调。

核心目标：

1. 在同一 SQLite 数据库下实现可预测、可审计、可恢复的并发调度。
2. 保持数据库结构简洁，优先使用表表达事实状态，视图只用于阅读聚合。
3. 数据库对象命名采用中文，保留 `uid_` 前缀作为机器标识字段。
4. AOE 负责控制面与提交协调，AOK/agent 负责执行与产出变更计划。

边界约束：

1. 不把并发控制逻辑散落到各事务内部。
2. 不依赖隐式锁行为作为调度策略。
3. 不把视图作为写入主契约。

## 二、设计原则

### 1. 表优先原则

1. 任务状态、请求状态、租约状态、心跳状态都必须落表。
2. 表是唯一写入契约；状态推进、恢复和审计都以表为准。
3. 任何调度判断都不得依赖临时内存态作为唯一来源。

### 2. 视图派生原则

1. 视图仅用于阅读聚合，例如任务全链路、阻断分析、决策统计。
2. 视图不得承接写入，不得作为状态机推进入口。
3. 视图列名保持中文语义，必要时提供 `uid_` 关联字段。

### 3. 命名一致性原则

1. 表名中文化。
2. 列名中文化。
3. 状态值中文化。
4. 除 `uid_` 前缀字段外，不新增英文业务字段名。

### 4. 单写协调原则

1. 多 agent 可并行读取与计算。
2. 对同一数据库的写入需经过 AOE 的租约与状态推进协调。
3. 写事务应短小且幂等，避免长事务占锁。

### 5. 声明与运行分离原则

1. EA、AA、TA 的 `json` / `md` 资产只用于声明角色契约、输入输出、审计字段与回退策略。
2. 实际调用必须发生在 AOE 主程序的时间步内，由主循环按需程序性唤起，而不是把文档资产本身当作执行器。
3. 运行时裁决结果必须回写请求表、决策记录或运行事件，不得只停留在对话文本或临时内存态。

## 三、角色模型

### 1. AOE（控制面）

1. 维护任务状态机。
2. 维护扫描时间步与逻辑时间步。
3. 管理事务请求队列。
4. 管理资源租约与执行者心跳。
5. 在需要时程序性调用 EA、AA、TA 等运行角色。
6. 协调提交顺序与故障恢复。
7. 输出审计事件与治理视图。

### 2. EA（调度角色）

1. 在逻辑时间步内读取业务状态面与请求状态面。
2. 生成或接收候选动作摘要并进行排序、裁剪、裁决。
3. 默认优先通过阿里百炼大模型给出调度判断；失败时回退到确定性优先级。
4. 产出标准请求创建计划、调度元数据和是否升级人工治理的结论。
5. EA 不直接替代事务执行器，不直接长事务写业务结果表。

### 3. AA / TA（执行协同角色）

1. AA 负责把候选动作转换为正式事务请求、运行配置和调用参数。
2. TA 负责领取租约、执行事务、回写结果、释放租约。
3. AA / TA 都由 AOE 主程序在逻辑时间步内按需唤起，不要求以独立对话代理常驻。

### 4. AOK / Agent（执行面）

1. 读取请求与配置。
2. 执行事务脚本与外部工具。
3. 产生执行结果与变更计划。
4. 回写请求结果与执行证据。

### 5. 数据库（状态面）

1. 保存控制面真相。
2. 提供可重放状态演进记录。
3. 保障跨进程可见性。

## 四、时间步模型

### 1. 扫描时间步

1. 扫描时间步是主循环的外层拍次，用于周期性重新观察当前业务状态与请求状态。
2. 一次扫描时间步通常包含：状态扫描、候选生成、调度裁决、请求消费、空闲判定。
3. 扫描时间步关注的是“何时再次扫描世界状态”，是控制面的时序单位。

### 2. 逻辑时间步

1. 逻辑时间步是一次扫描时间步内部的算法推进阶段。
2. 典型逻辑时间步链路为：观测状态 -> 生成候选 -> EA 裁决 -> AA 物化请求 -> TA 执行 -> 回写状态。
3. 逻辑时间步关注的是“系统内部按什么顺序推进决策和执行”，不是墙上时钟时间。

### 3. 二者关系

1. 扫描时间步决定 AOE 多久重新收敛一次当前世界。
2. 逻辑时间步决定每一拍内部 EA、AA、TA 如何协同推进。
3. 一个扫描时间步可以只跑一个逻辑时间步，也可以分解为多个内部阶段，但审计上应能还原为同一拍次下的完整状态推进。

## 五、状态模型

### 1. 事务请求状态

建议统一使用以下状态值：

1. 待调度
2. 待租约
3. 已租约
4. 执行中
5. 待提交
6. 已提交
7. 已完成
8. 已阻断
9. 已失败
10. 已取消

### 2. 租约状态

1. 已持有
2. 已释放
3. 已过期
4. 已完成
5. 已失败

### 3. 执行者运行状态

1. 空闲
2. 忙碌
3. 阻断
4. 离线

## 七、调度流程

### 1. 业务状态扫描

1. 从业务数据库读取当前真相，例如 `content.db` 中的流程状态、阅读状态、预处理状态和附件状态。
2. 从任务数据库读取待调度请求、租约状态、执行者心跳和最近审计事件。
3. 将业务状态面与请求状态面合并为当前拍次的候选输入。

### 2. 候选收集

1. 从事务请求表读取待调度请求。
2. 从业务状态面中推导尚未物化为请求的候选动作。
3. 形成统一候选池，并过滤已被有效租约占用或已存在等价签名的动作。

### 3. EA 调度裁决

1. AOE 在逻辑时间步中程序性调用 EA，对统一候选池进行排序或裁决。
2. EA 默认优先通过阿里百炼模型输出候选优先级与调度说明。
3. 若模型失败、超时或输出无效，必须回退到确定性优先级，不能阻塞整个主循环。
4. EA 裁决结果应写入请求元数据或运行事件，例如调度角色、决策来源、模型名和候选签名。

### 4. 租约发放

1. AOE 尝试为请求创建租约。
2. 成功后更新请求状态为已租约。
3. 绑定 `uid_执行者` 与租约过期时间。

### 5. 执行推进

1. 执行者回写心跳。
2. AOE 将请求推进至执行中。
3. 执行结果进入待提交或终态。

### 6. 提交收口

1. 成功执行：待提交 -> 已提交 -> 已完成。
2. 可恢复异常：转已阻断并保留证据。
3. 不可恢复异常：转已失败。
4. 释放租约并写入运行事件。

### 7. 过期接管

1. AOE 周期性扫描已过期租约。
2. 将租约标记为已过期。
3. 请求回退到待调度或待租约，等待重新领取。

## 八、冲突与一致性策略

1. 同一请求同一时刻只允许一个有效租约。
2. 调度冲突由租约判定，不通过脚本层临时互斥实现。
3. 使用幂等键避免重复执行产生重复副作用。
4. 通过预期版本与快照令牌支持乐观并发检查。
5. 写入失败必须保留错误类型、错误信息与栈摘要。

## 九、审计与治理

1. 每次状态推进写入运行事件。
2. 每次租约发放、续租、释放均写入事件。
3. 阻断事件必须保留阻断原因码、范围、是否需人工。
4. 决策部门视图只读聚合，不承接状态推进。
5. 当 EA 参与调度时，应保留调度角色、决策来源、模型标识、候选签名和回退原因。

## 十、与 AOE 现有能力的衔接

1. 保持既有任务状态机、决策部门、审计视图接口不破坏。
2. 优先在事务请求存储层补齐协调字段与租约能力。
3. 主循环优先复用既有 `run_task_request`、`run_task_requests`，增补“领租约-执行-提交流程”。
4. 项目级 runner 可以在调用 scheduler 之前，先完成业务状态扫描、EA 裁决和请求物化。
5. 对外 API 维持兼容返回，同时新增协调调度相关接口。

## 十一、验收标准

1. 同一请求不可被两个执行者同时领取。
2. 租约到期后可被其他执行者接管。
3. 请求状态推进路径完整且可审计。
4. 表名、列名、状态值符合中文主契约，仅 `uid_` 前缀保留。
5. 视图仅用于聚合阅读，不承担写入。
6. EA 可由主程序在逻辑时间步内程序性调用，且模型失败时仍可回退到确定性调度。
